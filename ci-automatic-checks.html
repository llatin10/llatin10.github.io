CI Automatic Checks — Wiki Registries & Platform-Type Sync

Two things happen automatically, and one thing happens on-demand. After every merge to mobile_dev, CI regenerates the Automation Coverage and Disabled Tests wiki pages straight from the test code — no PR, no conflicts. Separately, keeping the Jira Platform type field (customfield_11640) honest is a manual, Claude-driven step, because a GitHub runner can't reach the Atlassian MCP.
On this page: 1. Wiki auto-sync (post-merge) · 2. Run-summary banners · 3. Clearing the pending note · 4. The PR gate that used to exist · 5. Platform-type (--check / --sync) · 6. User story — a developer's PR, start to finish · 7. Other CI checks worth knowing

1. Wiki auto-sync — sync-test-registries.yml

trigger: push to mobile_dev

Runs after every merge to mobile_dev. It checks out the code, regenerates the registries from the test source, and pushes the result straight to the repo's GitHub Wiki — a separate, unprotected git repo, so the default GITHUB_TOKEN can push with no PR and no admin rights.

What it regenerates and publishes

  • python3 scripts/disabled_tests_report.py → wiki DISABLED_TESTS
  • python3 scripts/automation_coverage_report.py → wiki AUTOMATION_COVERAGE
  • python3 scripts/find_user_collisions.py --scope teambanking → wiki Known-User-Collisions
  • python3 scripts/jira_done_sync.py --refresh-pending-note — recomputes the delta of newly-automated tests since the last wiki snapshot and writes it into the <!-- JIRA-PENDING --> block at the top of AUTOMATION_COVERAGE.md

📖 Mobile Banking (index)

mobile-tests/wiki/Mobile-Banking

📖 Automation Coverage

mobile-tests/wiki/AUTOMATION_COVERAGE

📖 Disabled Tests

mobile-tests/wiki/DISABLED_TESTS

Both generated files are gitignored in the repo — nobody commits them by hand, and a developer never has to remember to regenerate anything. Concurrent PRs can no longer conflict over these files because they don't live in the repo at all anymore.

Concurrency guard

Both this workflow and Clear pending note (section 3) write to the same wiki repo, so they share a concurrency group: group: wiki-registries, cancel-in-progress: false. That serializes the two writers so two pushes can never race into a non-fast-forward conflict.

2. Run-summary banners (reusable, read-only)

Two small reusable workflows never touch Jira or fail a run — they just print a reminder into the calling workflow's Job Summary so whoever triggers a test run sees the current state at a glance.

workflow_calljira-sync-summary.yml

Checks out the wiki and echoes the <!-- JIRA-PENDING --> block from AUTOMATION_COVERAGE.md into $GITHUB_STEP_SUMMARY — capped at 15 rows (the wiki has the full list). Wired into every Android/iOS/custom test run (ios-test-develop-banking-uat, android-test-develop-banking-uat, custom-workflow, run-specific-tests).

workflow_callcandidate-sync-reminder.yml

Appends a static nudge: "Run /automation-coverage sync from jira to pull newly flagged candidates." Only wired into the two develop-banking-uat schedules (Android + iOS), not every run.

Both are continue-on-error: true — a summary write failing never fails the test run.

3. Clearing the pending note — clear-jira-pending-note.yml

manually triggered (workflow_dispatch)

After you run /automation-coverage sync to jira in Claude (see section 5) and confirm which tickets are now genuinely Done in Jira, this workflow trims those keys out of the wiki's pending-sync note so the run-summary banner stops nagging about tickets that are already fixed.

gh workflow run clear-jira-pending-note.yml --ref mobile_dev \
  -f keys="OZ-111452,OZ-111095,OZ-117467"

Evidence-based: only the keys you pass are removed from the note — anything omitted stays pending. Leaving keys empty clears the whole note. Internally it runs:

python3 scripts/jira_done_sync.py --clear-pending-note --keys "$KEYS" \
  --coverage-file ../wiki/AUTOMATION_COVERAGE.md

Shares the wiki-registries concurrency group with the post-merge sync workflow, so the two can't race.

4. The PR --check gate — retired in PR #1986

Historical note, not a current gate. Before #1986, AUTOMATION_COVERAGE.md and DISABLED_TESTS.md were committed to mobile_dev, and build-project.yml ran two blocking jobs on every PR: 
disabled-tests-registry:
  run: python3 scripts/disabled_tests_report.py --check

automation-coverage-registry:
  run: python3 scripts/automation_coverage_report.py --check

Since the files moved to the wiki and are now .gitignored, there's nothing left to check on a PR — the wiki simply catches up ~30s after merge. Both scripts still support --check (exit 1 if the output would differ) — useful for a local pre-commit sanity check, just no longer wired into any GitHub Actions job.

5. Platform-type field (customfield_11640) — --check / --sync

This is the piece that keeps the Jira "Mobile automation - banking" dashboard honest. It is not a GitHub Actions job — Jira runners can't reach the Atlassian MCP — so it runs manually via the /automation-coverage Claude command, backed by two scripts.

DirectionScriptWhat it does
Inbound
Jira → CSV		 jira_candidate_sync.py Pulls Xray Tests flagged Mobile / Candidate, Testing Level = Sanity, in-scope Domain, and reconciles them into regression-suite.csv so newly-flagged candidates can't stay off the backlog.
Outbound
code → Jira		 jira_done_sync.py Reads which OZ tests are automated and on which platform (from the same code scan the coverage registry uses) and flips their Jira ticket from Candidate to the correct Done … value.

Mapping (outbound)

Code statePlatform type set in JiraChild option id
Android ✅, iOS ✅Mobile / Done both platforms14046
Android ✅, iOS blankMobile / Done Android13961
Android blank, iOS ✅Mobile / Done iOS14045
Both blank (disabled everywhere)skip — don't touch—

Parent option is always "Mobile " (id 13959, note the trailing space — that's how Jira stores it). Only tickets currently at Candidate are touched; already-Done or Blocked tickets are left alone.

The --check flag (CI-style gate, run manually today)

python3 scripts/jira_candidate_sync.py --jira-api --check   # exit 1 if a Jira candidate is missing from the CSV
python3 scripts/jira_done_sync.py     --jira-api --check   # exit 1 if any automated test is still "Candidate" in Jira

Both scripts are dry-run by default; --write is the only flag that touches anything (CSV or Jira). Neither --check is currently wired into a GitHub Actions workflow — they need a live Jira token or the MCP, which a shared CI runner doesn't have — so today they're run by hand as a pre-flight before /automation-coverage sync from jira / sync to jira.

End-to-end flow

1
Merge lands on mobile_dev — sync-test-registries regenerates the wiki registries and refreshes the pending-sync note with any newly-automated tests.
2
Every test run echoes the pending note into its Job Summary (jira-sync-summary.yml) and, on the two scheduled develop-banking-uat runs, a reminder to pull new candidates (candidate-sync-reminder.yml).
3
Every few days, someone runs /automation-coverage sync to jira in Claude — dry-runs jira_done_sync.py against live Jira status via the MCP, applies the confirmed updates with editJiraIssue, then triggers clear-jira-pending-note.yml with the verified keys.
4
The bot PR from step 3 gets human approval and merges — the trimmed note shows up on the next test run, closing the loop.

6. User story — a developer's PR, start to finish

Dana picks up two things from her sprint: re-enable OZ-100111 (a Savings test that's been commented out since a bug was fixed) and automate OZ-123456, a brand-new test that's been sitting in the Jira Mobile / Candidate backlog since the last /automation-coverage sync from jira. To save setup time, she points her new test at userEmail: qa-savings-04@test.digibank.co.il — a login identity that SavingsWithdrawalLimitTest already uses elsewhere in the suite.

What Dana does

  • Re-enables OZ-100111 — removes the // DISABLED(bug): … comment and un-comments the @Test in SavingsAutoInvestPauseTest.kt.
  • Writes OZ-123456 — a new SavingsAutoInvestOptInTest.kt with @TmsLink("OZ-123456"), wired to a data row in the domain's CSV with userEmail = qa-savings-04@test.digibank.co.il (same value as another test's row).
  • Runs ./gradlew compileTestKotlin ktlintCheck locally, then opens the PR: "feat(savings): re-enable OZ-100111, automate OZ-123456".

What Dana sees in the PR

1
build_no_test check runs and goes green — it's the standard build, unrelated to the registries or Jira.
2
User-collision auto-serialize (TeamBanking) check runs — find_user_collisions.py --fix scans the domain's test-data CSVs, sees qa-savings-04@test.digibank.co.il now shared by two in-scope tests with no common lock, and adds a class-level @ResourceLock("user:qa-savings-04@test.digibank.co.il") to both SavingsAutoInvestOptInTest.kt and SavingsWithdrawalLimitTest.kt.
3
A new commit appears on her branch — chore(test): auto-serialize user collision via @ResourceLock [bot], pushed by github-actions[bot]. Dana needs to git pull before pushing anything else locally, or the next push will be rejected as non-fast-forward.
4
A PR comment shows up: "🤖 User-collision: @ResourceLock updated", listing the exact lines added, and a link to the Known User Collisions wiki page. It suggests a dedicated user as the alternative fix if she'd rather not share identities.
5
Nothing else blocks the merge. There's no disabled-tests-registry or automation-coverage-registry gate to satisfy — that check was retired in #1986 (section 4). Dana gets a review and merges.

If Dana prefers a dedicated user over sharing one, she can revert the bot's lock, swap in a fresh test user, and push again — the collision check simply won't find anything to fix on the next run.

What happens behind the curtain — after she merges

1
~30 seconds later — sync-test-registries fires on the push to mobile_dev:
  • DISABLED_TESTS.md is regenerated — OZ-100111's row disappears, since its @Test is no longer commented out.
  • AUTOMATION_COVERAGE.md is regenerated — OZ-123456 flips from a curated "not-yet-automated" backlog row to ✅ Automated, with ✅ under Android and iOS (assuming both run). OZ-100111's ✅ marks return too.
  • Known-User-Collisions.md is regenerated — the shared identity now shows up as resolved via @ResourceLock, not an open collision.
  • All three are pushed straight to the wiki — no PR, no review needed for this step.
2
The pending Jira-sync note updates too — jira_done_sync.py --refresh-pending-note notices OZ-123456 is now automated in code but still shows Mobile / Candidate in Jira, and adds it to the <!-- JIRA-PENDING --> block at the top of the wiki's AUTOMATION_COVERAGE.md. (OZ-100111 was already Done in Jira from before it was disabled, so it doesn't need a Jira update.)
3
Next Android/iOS/custom test run — whoever triggers it sees OZ-123456 listed in the Job Summary banner from jira-sync-summary.yml: a nudge that Jira hasn't caught up yet.
4
A few days later — a maintainer runs /automation-coverage sync to jira in Claude. It dry-runs jira_done_sync.py against live Jira, confirms OZ-123456 is genuinely running on both platforms, and applies editJiraIssue to flip customfield_11640 from Candidate (13960) to Done both platforms (14046).
5
The note gets trimmed — the maintainer triggers clear-jira-pending-note.yml -f keys="OZ-123456", which opens a one-file bot PR against the wiki removing just that key. A human approves it, it auto-merges, and the next test run's banner no longer mentions OZ-123456 — code, wiki, and the Jira dashboard all agree.

7. Other CI checks worth knowing about

  • User-collision auto-serialize (build-project.yml → user_collision_check) — non-blocking, PR-time. If a PR introduces two tests sharing a login identity, it auto-adds @ResourceLock, commits it to the PR branch, and comments. The Known-User-Collisions wiki page it reads from is refreshed post-merge by the same sync-test-registries workflow.
  • Android / iOS locator impact check (android-locator-impact-check.yml, ios-locator-impact-check.yml) — triggered by repository_dispatch from the app repos when locator ids change; scans which tests are impacted and comments the report back on the app PR.
  • Amazon Q PR skip (build-project.yml → check-author) — skips the build job entirely for PRs authored by amazon-q-developer[bot] (auto-heal PRs get their own validation via validate-auto-heal-pr.yml instead).
